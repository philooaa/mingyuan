## 二、两套实现对应关系

| 业务 | 当前本地实现 | PR #6 的一对一底层 |
| --- | --- | --- |
| 孩子身份 | `edu_student_lesson_account.account_id`，报名绑定 `lesson_account_id` | `edu_student.student_id`，报名绑定 `student_id` |
| 课包账户 | 每个孩子独立账户，允许跨学科使用 | `edu_lesson_package` 定义学科课包，`edu_student_package` 保存学员持有课包 |
| 课次事件 | `edu_lesson_credit_event` | `edu_lesson_unit_log` |
| 课程／开放时段 | `edu_course_schedule.class_mode='2'`，机构固定两小时时段 | `edu_one_to_one_slot`，真实起止时间、教室、教师 |
| 预约记录 | `edu_enrollment`，具体 `class_date`，保留教师确认／取消处理 | `edu_one_to_one_booking`，预约后为 `BOOKED`，没有教师审批阶段 |
| 额度处理 | 预约暂占，确认到课后正式消耗；教师处理取消后释放暂占 | 预约立即扣次，课前取消自动返次 |

| 收款事实 | 本地 `EnrollmentPaymentService` 登记报名支付状态和操作事件 | `TuitionService` 管理付款记录、核验、收据、退款、优惠券和账单快照 |

两套孩子 ID、课包 ID、报名 ID、预约 ID 不能按数值相同视为同一个对象。学科中文名称与字典编码也需显式转换。

## 三、发现的问题及建议

### 3.1 高优先级：团队报名流程丢失现有一对一分流

团队 `MiniAppParentServiceImpl.enroll()` 已删除调用 `singleService.enroll(body)` 的分流，统一走普通班课报名；但 `MiniAppParentController` 仍保留 `/single/lessons`、取消申请及历史接口。

其 `countScheduleAvailable` 未排除 `class_mode='2'`，普通插入也不保存 `class_date`。因此直接提交一对一排课 ID 可能被当作班课报名，按教室容量扣名额，绕过具体日期的唯一名额和教师确认。

团队小程序报名页同时不再展示本地已有的课程类型选择；这解释了只运行 main 的同学看不到该选项，不能据此认定功能分支漏传。

**建议：** 保留课程类型选择、具体日期和一对一服务分流；班课路径显式拒绝一对一排课，不能仅靠前端隐藏。

依据：[团队报名服务](https://github.com/shengyinHHU/MingYuan/blob/ce2e1f8b5e7f4faaf4f6223ad27ec7779277fad6/RuoYi-Vue-master/ruoyi-system/src/main/java/com/ruoyi/system/service/impl/MiniAppParentServiceImpl.java#L74)、[普通报名 Mapper](https://github.com/shengyinHHU/MingYuan/blob/ce2e1f8b5e7f4faaf4f6223ad27ec7779277fad6/RuoYi-Vue-master/ruoyi-system/src/main/resources/mapper/system/MiniAppParentMapper.xml#L199)。

### 3.2 高优先级：付款有两个写入入口，资金事实可能不一致

本地 `EnrollmentPaymentService.mark()` 直接更新 `edu_enrollment.pay_status`，没有生成队友的 `edu_tuition_payment`、收据或退款记录。团队 `FinanceEnrollmentGuard` 则明确禁止普通报名编辑修改支付状态，要求通过财务服务登记和核验。

合并后若同时保留两个写入口，可能出现报名显示已付／已退，但财务没有成功收款／退款事实。团队还存在“部分退款”“已减免”等状态，本地三种状态的归一化不能覆盖它们。

**建议：** 收款、退款、收据和优惠券使用队友的财务服务作为唯一写入来源。本地交易管理可以保留为账户视图；付款按钮接到财务入口，不能继续直接修改支付状态。课程价格仍未确定，不自动补金额、收据或已支付记录。

依据：本地 `EnrollmentPaymentService.mark()`；[团队编辑保护](https://github.com/shengyinHHU/MingYuan/blob/ce2e1f8b5e7f4faaf4f6223ad27ec7779277fad6/RuoYi-Vue-master/ruoyi-system/src/main/java/com/ruoyi/system/finance/FinanceEnrollmentGuard.java#L37)。

### 3.3 高优先级：取消报名必须同时遵守预约和财务约束

团队 `MiniAppParentServiceImpl.cancelEnrollment()` 和后台批量取消已统一调用 `TuitionService.cancelEnrollment()`，不再判断一对一具体日期或教师取消申请。该财务服务最终关闭报名并释放排课人数，没有调用本地课包暂占释放、日期名额或一对一事件服务。

另一方面，本地 `OneToOneEnrollmentService` 的教师取消流程没有检查团队的成功收款、结果未知付款和退费流程。只保留任意一边都会漏掉另一边的约束。

**建议：** 一对一仍采用“家长申请 → 教师处理”；在统一事务中处理预约状态、日期名额、课次释放及事件。涉及现金收退款时调用财务服务的受保护流程；退款结果未知不能擅自视为成功。已取消重试不得重复释放或返次。班课保留团队的财务安全取消。

依据：[团队取消及收款保护](https://github.com/shengyinHHU/MingYuan/blob/ce2e1f8b5e7f4faaf4f6223ad27ec7779277fad6/RuoYi-Vue-master/ruoyi-system/src/main/java/com/ruoyi/system/finance/TuitionService.java#L1386)、[关闭报名及释放人数](https://github.com/shengyinHHU/MingYuan/blob/ce2e1f8b5e7f4faaf4f6223ad27ec7779277fad6/RuoYi-Vue-master/ruoyi-system/src/main/java/com/ruoyi/system/finance/TuitionService.java#L1266)。

### 3.4 高优先级：孩子身份和课包不能维护两套余额

本地孩子管理、报名选择和账户视图共用 `lesson_account_id`；团队底层使用独立 `student_id` 和按学科课包。两边的记录不会自动同步，按姓名自动合并也会误合并同名孩子。

团队 `LessonService.book()` 预约即扣次，`cancel()` 课前自动返次，`complete()` 由管理员登记完成。与已确认的跨学科课包、暂占后消耗、教师处理取消规则存在直接差异。

**建议：** 现阶段保留已经接入页面的本地预约／课次规则，不同时启用另一套预约写入。后续由团队确定一个孩子身份来源和一个课次账本，使用明确关联迁移旧记录；保留余额、暂占、消耗、操作人及原事件，不以同名或相同 ID 自动关联。若采用团队 `edu_student` 作为统一档案，应为现有课次账户建立可核验的关联，不能再建第三份学生表。

依据：[团队预约、取消和完成](https://github.com/shengyinHHU/MingYuan/blob/ce2e1f8b5e7f4faaf4f6223ad27ec7779277fad6/RuoYi-Vue-master/ruoyi-system/src/main/java/com/ruoyi/system/lesson/LessonService.java#L147)。

### 3.5 高优先级：教师学科、等级仍有两个来源

教师资料 PR #8 已改为 `edu_teacher_profile`。团队另一套 `LessonService.book()` 仍从 `sys_user.teacher_level` 计算扣次，`setTeacherLevel()` 仍更新该系统表；其迁移也会添加 `teacher_subject`、`teacher_level`。

本机保留了旧列，且只读核对发现等级来源已有不一致。直接用两套服务会出现后台修改了教师等级、一对一扣次却使用旧等级的问题。

**建议：** 教师学科和等级统一调用 `EduTeacherProfileService`，沿用后台导入及精英 1／资深 2 的快照规则。兼容迁移不再向 sys 表添加业务字段。已有旧列先保留，不为整理冲突直接删列；旧值也不覆盖已经维护的新资料。

依据：[团队旧等级读写](https://github.com/shengyinHHU/MingYuan/blob/ce2e1f8b5e7f4faaf4f6223ad27ec7779277fad6/RuoYi-Vue-master/ruoyi-system/src/main/java/com/ruoyi/system/lesson/LessonService.java#L162)。

### 3.6 高优先级：迁移索引与具体日期报名不兼容

团队财务迁移创建 `uk_edu_enrollment_once(schedule_id,parent_id,student_name,active_enrollment_guard)`，未包含日期；另一套一对一迁移将其中姓名替换为学生身份，仍未包含具体日期，因为它把实际预约放在另一张 booking 表中。

本地使用 `uk_single_lesson_seat(schedule_id,class_date,active_lesson)` 及独立的班课重复约束。同一孩子在同一历史重复课程下报名不同日期，在本地是合理业务，团队新增的唯一索引会阻止这种情况。当前只读检查未发现会立即触发该分组重复的数据，但后续报名仍存在约束冲突。

**建议：** 单独编写经核对的兼容迁移，区分班课报名唯一性、具体日期一对一座位和课包账单。部署前验证旧数据及外键，不直接串行执行两套原始迁移。MySQL DDL 不能假设整体失败会自动回滚。

依据：[团队财务唯一索引](https://github.com/shengyinHHU/MingYuan/blob/ce2e1f8b5e7f4faaf4f6223ad27ec7779277fad6/database/migrations/20261007_tuition_finance.sql#L237)、[另一套一对一迁移](https://github.com/shengyinHHU/MingYuan/blob/ce2e1f8b5e7f4faaf4f6223ad27ec7779277fad6/database/migrations/20261010_one_to_one.sql#L222)。

### 3.7 接入风险：两套时段占用检查未统一调用

本地 `ScheduleAvailabilityService` 使用机构固定两小时时段，查询现有排课和调课。团队 `LessonConflictGuard` 检查 slot／booking 与普通课程，但 `saveSlot()` 仅验证两小时长度，并不限定机构固定时段。

已检查团队生产代码引用：`LessonService` 尚无 Controller 接入；`LessonFinance` 尚未被 `TuitionService` 调用；`LessonConflictGuard` 尚未接入普通排课／调课服务。因此这些属于接入时必须解决的问题，不能宣称团队当前已经实现完整双向冲突保护或课包收款联动。

**建议：** 使用一个资源占用服务，统一教师 → 教室 → 排课／预约等锁顺序及占用来源；发布即占用，班课新增、修改、调课及一对一发布／预约都进行反向核验。保留已确认的固定时段、空闲教室选择、不连续开多周规则。

### 3.8 接入风险：个人账户未归集团队财务记录

本地 `ParentAccountService.records()` 目前聚合报名、课次事件和商城订单／事件，没有团队课程收款、收据、退款或优惠券来源。即使保留双方页面，也不会自动形成完整账户视图。

**建议：** 账户视图读取队友现有财务查询服务，付款／退款操作跳到已有页面；避免再造收据、优惠券和退款表单。课次消耗不能当作现金收入。待办角标继续只统计约定的有效单次付费未处理报名，详细财务状态应由账单及收款事实提供。

### 3.9 协作注意：开发登录默认行为有变化

团队 main 把开发登录开关从“local profile 且 mock 开启”放宽为仅 mock 开启，并允许未选教师时寻找一个默认教师。现有选择教师 ID 的能力仍在，不能误报为教师隔离全部消失。

**建议：** 合并时保留显式教师选择、角色会话恢复、后端重启失效和资源归属校验；开发环境开关变化单独确认部署用途，不能因保留财务代码就静默改变已确认的教师登录方式。

本地已修改文件与团队 main 相对当前 HEAD 的修改交集共 15 个。这是共同修改清单，不等同于 Git 一定会报告的文本冲突数量；新增文件间的业务重复也不在此数量内。

## 五、建议的整合顺序与验证

1. 先保存当前未提交工作的可恢复副本，再在隔离整合环境处理团队 main；不直接覆盖当前工作区。
2. 保留 PR #9 的 WiFi 打卡、复核、作业批阅及附件修复，保留 PR #6 的收费财务、优惠券、收据、退款；分别验证页面注册和原角色权限。
3. 保留本地已确认的一对一教师发布、固定时段、空闲教室、教师隔离、报名确认和取消处理；恢复团队 main 丢失的一对一分流与类型选择。
4. 确定唯一孩子身份和课次账本后，再衔接财务；另一套未接入的一对一底层不能与现有写入流程同时启用。
5. 先在隔离数据库测试兼容迁移，检查报名唯一索引、金额快照、付款退款保护及现存关联，再安排实际库更新。
6. 完成以下交叉回归后再形成整合提交／PR：
   - 同一孩子报名同一课程不同日期；改名不绕过同日期查重；同名孩子不能误合并。
   - 班课与一对一发布、调课、预约竞争同一教师／教室，只有一个成功。
   - 精英／资深分别暂占 1／2 次，后台等级变化不改旧预约快照。
   - 取消申请、批准、重复提交、已完成记录、付款未知及退款未知状态均不重复释放或返次。
   - 家长只看本人孩子／账单；教师只处理本人课程；管理员通过财务服务登记。
   - 收款、收据、退款、优惠券在账户视图可追溯，原财务金额和历史记录不被覆盖。
   - 教师切换、管理员切回教师、后端重启后的会话行为及原 WiFi／作业流程正常。

本次完成的是静态代码对照、远端提交核对及实际数据库只读核验，**尚未执行合并后的构建或联调，也未将本文建议视为已经实施**。
