# 老带新

## 已确认范围

推荐关系以家长稳定用户ID关联。绑定只产生待达标关系；首次有效课程报名和后台成功收款均满足后，才产生一条待奖励审核记录。首次后台确认时间决定7天补绑窗口，退款或后续付款不重置。历史收款补录不能重获新人资格。零元减免不构成收款；本机local/test模拟环境可计入模拟收款，正式环境只计真实收款。

管理员只在首次收款前纠错，必须记录原因；收款后的关系及首次补绑立即锁定。奖励按推荐记录、接收人、模板防重，同一家长跨关系可获同款奖励券。绑定、达标、发券和异常分别查询；家长仅查看本人范围。

## 一致性与补偿

绑定和纠错共用业务项目行锁，防止并发循环；首次收款事实固定保存并保留毫秒精度。达标记录对关系唯一。发券前锁定并重新核验报名、收款、累计成功退款与家长资格，再复用优惠券服务；发券和来源记录在同一事务提交。批次指纹包含完整推荐记录和接收人组合，预览人数按家长去重、发券数量按奖励明细统计。

定时扫描持久化绑定和达标记录，补偿未触发/失败的达标检查，并生成取消/全额退款异常；不能只扫描新建付款ID。异常处理及人工撤回保留原因、操作者、时间和结果，不自动追款。

推荐事务使用READ_COMMITTED，发券按排课、报名、付款顺序加锁后再读成功退款累计额，避免等待财务锁后仍看到旧快照。收款快照兼容增加confirmationEnrollmentActive，记录收款确认当时的有效报名事实；不增加收款对推荐表的依赖，不回写旧成功收款。首次收款时已绑定且曾达标，随后推荐登记失败、报名取消或全退，补偿仍重建达标历史和异常；绑定时已经取消或全退的报名不补造达标记录。已处理的取消异常不能掩盖后续全额退款异常。

定时补偿每30秒处理一批绑定并循环重试；正常收款确认及历史核验提交后立即尝试核验。批量发券结果不确定时保留原始请求及批次编号，显式回滚拒绝后必须重新预览。账号或角色切换后，旧查询、角标和操作响应不能写入新账号页面。

## 数据库与协作

使用edu_业务表和增量SQL，不修改sys表结构。仅补菜单和角色权限数据。数据库变更须先备份并在随机副本验证，原业务行数及原字段值核对保留。本机配置、密码和整库备份不提交；通过团队功能分支与PR交付。

| 新表 | 用途 |
| --- | --- |
| edu_referral_program | 启用时点及推荐事务并发锁。 |
| edu_referral_profile | 家长推荐码、历史用户标记和首次确认收款时点。 |
| edu_referral_binding | 一对一推荐关系、锁定时点及纠错历史。 |
| edu_referral_record | 首次达标推荐及审核状态，与绑定记录分开。 |
| edu_referral_reward_batch | 管理员批量发券请求及幂等指纹。 |
| edu_referral_reward | 每条推荐、接收人、模板的奖励及操作历史。 |
| edu_referral_anomaly | 取消、全退和资格异常的待处理记录及核查结果。 |

修改现有edu_user_coupon：增加推荐来源、普通发券生成身份；普通模板/家长唯一限制保留，推荐奖励按关系单独防重。来源同时外键引用奖励ID、家长ID和模板ID，限制来源不一致；业务历史均使用RESTRICT外键，防止删除破坏历史。不修改sys_user等系统表结构。

## 入口与使用

- 家长首页“邀请好友”：复制推荐码、确认推荐人、绑定及补绑期限、本人关系与奖励记录，跳转原“我的优惠券”。
- 小程序管理员首页“老带新管理”：绑定记录、推荐列表、发券记录和异常待处理，右上角显示待奖励审核及异常数量。
- 若依“系统管理 → 老带新管理”：相同四类管理流程，支持用户ID精确查询、关系角色筛选、批量勾选、接收人预览和人工核查。
- 管理员菜单权限edu:referral:manage；服务层仍核验实际管理员。家长仅本人范围，教师不能操作推荐管理。
- 开发环境使用原课程财务流程确认MOCK收款；正式环境只计REAL正额成功收款。已有“已支付”文字标签不等同于财务收款事实，历史凭据仍走原历史核验流程。

## 多家长开发测试入口

补充GET /miniapp/dev/parents和登录参数devParentId，保留旧家长、教师和管理员登录调用方式。家长选择只在local/test且启用模拟登录时开放；生产环境即使误开模拟标志也拒绝新选择接口。仅可选启用、未删除的独立家长账号，不能借此取得教师或管理员身份。复用既有用户与角色服务，不改sys结构。

5. 分别切换A/B查看各自奖励与我的优惠券，核对接收范围；重复发同记录、同接收人、同模板应受防重限制。
