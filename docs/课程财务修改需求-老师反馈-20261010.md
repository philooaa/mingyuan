# 课程财务修改需求：老师反馈整理

日期：2026-10-10  
状态：本次财务修改已实现并部署到本地开发库（2026-10-11）；后台、网页与小程序代码已提交本地 Git。分任务测试／审查及页面编译完成，按用户要求不再追加整体多轮审查。尚未推送 GitHub，微信真机体验待人工验收。
依据：老师最新修改意见及退费详情截图。本文新要求优先于此前单管理员退费流程与课程线上支付设想。

## 1. 修改范围和原则

1. 课程收费在线下进行，小程序不收课程学费，不预留真实微信课程支付入口。系统只记录收费、由教务／管理员确认收款并生成留档及收据。
2. 资料商城仍采用微信支付业务流程，不改动商城订单、支付和确认逻辑。当前代码仍是模拟支付与支付入口，真实微信商户支付尚未接通；老师认可流程不等于已接通真实支付。
3. 课程退费改为两级处理：家长提交申请 → 教务确认金额并标记已阅 → 管理员确认已退款 → 结束。
4. 家长不填写金额、不提供退款截图，不承担退款执行或到账核对操作；提交后只查看进度及最终退款金额。
5. 保留已有业务通知、进度展示、收费留档、收据、优惠券与其他课程的正常学习功能。不能把单次／单科退款等同于注销家长或退出全部课程。
6. 优先复用用户、角色、报名、收费、退费、课包等现有表，不为每个动作新建业务表。
7. 最初整理阶段仅新增本需求文档；用户随后已授权按本文开发。开发不自动推送 GitHub PR，不覆盖旧数据库或历史成功退款。

| 项目 | 已核对的当前情况 | 后续修改 |

| 优惠券发放 | 可选择已有家长批量发放，每批 1～100 人；家长筛选只有账号／昵称 | 增加孩子年级、学科联合筛选、勾选及全选 |

## 3. 课程收费：仅线下确认

### 3.1 家长端

- 展示课程报名、待确认收费／已确认收费、收据与退费入口。
- 不展示“微信支付”“模拟支付”“立即缴费”等课程在线付款按钮。
- 如需说明，使用“课程费用请联系教务线下缴纳”，不显示“微信支付接口尚未开通”等技术提示。
- 可查看金额及收款状态，但家长不能将账单自行标记为已收款。

### 3.2 教务和管理员端

- 保留／复用线下收费确认接口，记录报名、实际收款金额、收款日期、收款方式、经办人及备注。
- 教务、管理员根据实际配置的菜单权限使用；后端角色校验也必须允许授权教务，不能只放开按钮。
- 现金、银行转账、微信线下收款属于人工登记渠道，不是小程序微信支付。
- 实际确认收款后更新账单并生成收据；重复点击不得重复记账或重复激活课包。
- 零元减免、历史账单核验继续保留，不伪造现金付款。
- 老师未要求删除已有收款凭证；本次只明确家长无需提供退款截图，不扩大为删除所有财务凭证。

## 4. 新退费流程

```text
家长选择孩子及对应课程／退款范围，填写原因等信息（不填金额）
    ↓
等待教务确认金额
    ↓
教务查看申请，填写退费金额及说明，点击“确认金额／已阅”
    ↓
等待管理员办理退款
    ↓
管理员在线下完成退款，核对本申请和金额，点击“已退款”
    ↓
退款完成：家长看到退款金额、完成时间和进度通知，不需要再操作
```

“已阅”是业务审核动作：必须先确认金额才能流转，不能仅打开详情就自动通过。“已退款”表示工作人员对实际线下退款事实的登记，不会自动向微信发起资金退款。

### 4.1 家长提交

- 保留课程、孩子、原因、联系方式等现有非金额信息，并增加必要的退款范围选择。
- 移除金额输入、金额校验、金额确认弹窗和历史重试缓存中的金额要求。
- 后端不得信任家长伪造的金额；金额由教务填写，未定金额为 `NULL`，不是 0 元或系统猜测金额。
- 正式提交后家长只查看，不再显示撤回、上传退款截图、确认到账等按钮；上一版家长撤回功能被本要求覆盖。
- 重复点击／断网重试仍使用同一申请标识，不产生重复申请。

### 4.2 教务处理

- 待办列表展示孩子、课程、范围、申请原因、原实收、历史已退、处理上限。
- 点击处理弹出金额与说明表单；金额必须大于 0，不得超出当前实际可退余额。
- 单次或部分退款不默认套用“全部剩余课程价格”；金额由教务按机构规则确认。
- 教务提交后固定金额、记录经办人及时间，流转给管理员；家长至少看到“等待管理员办理退款”。
- 申请不成立时允许驳回并填写理由，通知家长；驳回不得产生资金退款或取消课程。

### 4.3 管理员处理

- 展示教务确认的金额、范围和说明。
- 线下退款后点击“已退款”，二次确认金额与申请对象，服务器记录管理员及完成时间。
- 不再提供独立“执行退款 → 处理中 → 核对到账结果”流程，也不要求家长或管理员为该课程流程上传退款截图。
- 管理员发现错误时可驳回并填写理由；不直接静默修改教务金额。需要修改时按确认后的重新处理规则办理。
- 完成后更新退款台账、账单净收款和对应教学状态；重复确认必须幂等，不二次扣减。
- 原始收款事实、已发收据快照及成功退款事实不得篡改；保留退款历史，不直接删除原收据。

### 4.4 两级权限

- 复用 `sys_user`、`sys_role`、`sys_user_role`、`sys_menu`、`sys_role_menu`，不另建教务或管理员用户表。
- 分开配置“教务确认金额／已阅”和“管理员已退款”权限，两个步骤缺一不可，不能管理员直接跳过教务步骤。
- 新流程是两级动作，不自动等同于两个不同账号。是否强制不同人员处理需老师确认；不得擅自恢复导致单管理员再次卡住的账号不相等限制。
- 教务现有角色编码需在实施前核对，不凭空指定新角色。

## 5. 前端展示调整

- 截图中红框的“计算快照”整行隐藏，所有业务页面不展示 JSON、规则版本和内部字段名称。
- 后端 `calculation_snapshot` 保留，用于审计、幂等和规则追溯；隐藏展示不等于删除数据。
- 对外状态改为：等待教务确认金额、等待管理员办理退款、已退款、申请未通过。
- 家长待审核时显示“退费金额待教务确认”；管理员完成后显示“已退费 ×× 元”。
- 移除课程退款的“核对退款到账结果”、结果未知处理入口、必传退款凭证和旧的单管理员开发提示。
- 技术异常显示可读提示，历史兼容状态只用于处理旧记录，不能继续生成新的旧流程记录。

## 6. 部分退费与继续上课

### 6.1 退款范围与金额分离

退款金额多少和是否退出课程是两回事。应明确区分：

| 业务场景 | 金额处理 | 教学处理 |
| --- | --- | --- |
| 不退课的费用调整／部分退费 | 教务确认金额，管理员登记已退款 | 保留对应课程报名，其他课程不变 |
| 两门课退一门 | 只关联所选课程的报名及其缴费 | 只取消该门课；另一门课、孩子和家长账号继续有效 |
| 10 次课只退某一次请假课 | 明确关联课次／预约，由教务确认金额 | 只处理该课次，其他课次和剩余权益保持正确 |
| 整门课／整包退出 | 以实际收款和已退金额为上限确认 | 只关闭所选报名／课包，保留历史记录 |

### 6.2 当前覆盖判断

普通课 `PARTIAL` 退款完成不会调用退课逻辑，已支持“退钱但继续上课”；`WITHDRAWAL` 只作用于本次关联的报名，不取消家长其他报名。

但是“某一次请假课”的精确退款尚不能宣称完成：当前申请缺少课次关联、单次可退额度及防重复规则。一对一 `LessonFinance.close()` 当前按退款关闭整个剩余课包，也不满足只退某一次、其他权益继续保留的要求，必须调整。

### 6.3 防止重复补偿

- 一对一课前取消已按既定规则自动返还 1 或 2 次。若同一课次又现金退费，不能默认既返次数又退钱。
- 单次现金退款需关联该课次和实际课包，并明确是否收回已返还次数；不得使用假定“每次都扣 1 次”的规则。
- 退款申请期间仅锁定必要的可退金额／课次权益，不因单次申请冻结其他课程或整包全部可用权益。
- 整包退出仍按整包处理；单次和不退课退费不能走原整包关闭逻辑。
- 涉及已返次数、已用次数、未来预约时，后台必须校验并原子更新课次／余额／日志，不能仅改页面状态。
- 具体请假退款政策、课次单价、退次还是退钱、未使用次数的计价方式属于待确认规则，不由程序自行推定。

## 7. 优惠券：按孩子年级与学科筛选批量发放

### 7.1 页面操作

1. 选择已有优惠券模板。
2. 按孩子年级、学科筛选，可继续按已有家长名称／账号搜索。
3. 展示家长及命中筛选的孩子、年级和学科，允许逐行勾选。
4. 提供“全选当前页”和“一键全选筛选结果”，明确已选人数及筛选范围；不把当前页选择冒充全部筛选结果。
5. 确认模板、目标家长人数、发放说明后批量发放，展示成功／失败结果并保留发放记录。

### 7.2 数据来源与保护

- 收券主体仍是已有家长 `sys_user`，复用 `edu_user_coupon`，不新建家长名单表。
- 学科、年级优先通过孩子有效报名关联 `edu_course_schedule` 的 `subject_name`、`grade_name`。尚未部署的一对一迁移定义了 `edu_student.grade_code`，但当前业务库不能假设此表及年级数据已存在；历史报名仅学生姓名时不能猜测跨记录是同一个孩子。
- 年级和学科必须命中同一孩子／同一相关报名，不能用孩子 A 的年级和孩子 B 的学科拼出假命中。
- 同一家长有多个符合条件的孩子，名单显示命中明细，但家长收券去重；“每个孩子一张”并非本次要求。
- 名单筛选与券使用范围是两个概念：按学科筛人不会自动修改模板的适用规则。
- 全选只覆盖当前筛选范围，发放前固定已选名单／批次标识，后台重新校验账号及权限。
- 当前后端每批最多 100 名家长，全选超过 100 时须安全分批，报告各批结果；失败重试保留原批次标识，防重复发券。
- 改变筛选条件后清空旧选择或明确提示，不静默给旧筛选的家长发券。

## 8. 数据库调整建议（待实施，不是已经迁移）

### 8.1 复用表

- `edu_enrollment`：报名／课程账单，继续作为课程和课包收费归属。
- `edu_tuition_payment`：已确认线下收款事实。
- `edu_tuition_refund`：申请、教务确认金额、管理员已退款的全流程。
- `edu_tuition_receipt`：收据及历史快照。
- `edu_class_sign_in`、`edu_one_to_one_booking`、`edu_student_package`、`edu_lesson_unit_log`：在确有对应课次／课包时关联教学处理；普通课具体请假复用签到表，不使用报名唯一的 `edu_attendance` 冒充多课次。
- `edu_coupon_template`、`edu_user_coupon`：券模板及已有家长的持券／发放记录。
- 若依现有操作日志：保留工作人员处理记录，不因流程简化丢失追溯。

### 8.2 退费字段和约束

| 字段或数据 | 建议处理 | 原因 |
| --- | --- | --- |
| `requested_amount` | 新申请允许 `NULL`，保留旧记录原金额 | 家长不报价，不能填写假金额满足旧约束 |
| `approved_amount` | 复用为教务确认的退费金额 | 不新增另一套相同金额；最终管理员按此金额登记 |
| `reviewer_id`／`review_time`／`review_remark` | 复用为教务处理人员、时间及说明；旧记录保留原语义 | 原审核字段可复用，历史不能伪造教务处理 |
| `executor_id`／`completed_time` | 复用为管理员已退款确认人员、时间 | 记录最终线下退款事实 |
| `refund_status` | 建议增加 `WAIT_EDU`、`WAIT_ADMIN`；完成复用 `SUCCESS` | 区分两级待办，不把 NULL 金额当已审核 |
| 退款范围／课次关联 | 必要时增范围字段及可空课次／预约引用 | 区分费用调整、单次退费、退出课程；实施时按实际表结构定字段 |
| `calculation_snapshot` | 保留但不展示原始 JSON | 审计、课次和金额依据可追溯 |
| `evidence_key`／第三方退款流水 | 新课程退款不强制填写，旧凭证仍保留 | 本流程是线下事实登记，不是微信退款回调 |

当前数据库要求 `requested_amount > 0` 且非空，批准金额不能超过申请金额，并限制旧状态枚举。因此不能只删前端金额框，必须同步调整 NOT NULL、CHECK、状态校验、金额上限、保留额度计算和幂等请求摘要。

未定金额申请不以 0 元占额度：同一缴费及退款范围需要防重复申请；教务定金额时，锁定账单／缴费，核对历史成功退款及其他已定金额申请后占用额度，管理员完成时复核。未知范围的旧记录先人工核对，不自造课次。

### 8.3 迁移要求

- 新增独立增量 SQL，不修改已执行迁移冒充升级；不删表、不重建业务库。
- 停后端并备份，专用测试库验证首次及重复执行，再更新目标库。
- 已完成退款和已确认资金事实保持不可篡改。
- 旧 `PENDING_REVIEW`／`APPROVED`／`PROCESSING`／`UNKNOWN` 等记录逐类兼容或人工处理，不能批量标记已退款，不能自动给旧记录补教务人员。
- 和一对一未完成迁移协调执行顺序，不能为调整财务重新执行旧迁移覆盖新约束。

## 9. 接口调整方向

以现有接口为基础改语义或增加少量阶段接口，具体路由在实施前核对。

- 家长提交：绑定本人孩子及对应报名／课次，只提交范围、原因及必要联系方式，不提交金额；返回等待教务处理。
- 教务确认：接收退款 ID、确认金额、说明及版本信息，校验教务权限和阶段后流转。
- 管理员已退款：接收退款 ID、版本及必要备注，金额取已确认记录，不信任前端自行换金额；事务内完成记账与教学更新。
- 家长查询：返回可读阶段、最终金额及时间；不要求家长调用撤回或确认到账接口。
- 课程收款确认：仅授权教务／管理员使用；不接微信统一下单、支付通知或课程微信退款。
